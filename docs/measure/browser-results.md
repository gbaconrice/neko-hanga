# ブラウザでの実測（実際の画面を、自動のタッチで操作）

本物の画面のつまみと「刷る」ボタンを、自動のタッチ入力で操作して時間を測りました。
目的は「操作そのものに何秒かかるか」と「画面の側に、プレイヤーではどうにもならない待ち時間がないか」を確かめることです。
紙を解く力は測っていません（正解は `__pz.cur()` から読んでいます）。

## 必ず読んでほしい前提（これは何を示さないか）

- **自動入力の速さは、人の操作ではありません。** 見て考える時間がゼロで、迷いも打ち間違いもありません。ここでの秒数は「指の動きと画面の反応だけの下限」に近いものです。人が遊んだ結果ではありません。
- **クラウドの Linux 上の headless Chrome は、iPhone でも GRAVITY でもありません。** 実機の WebView・タッチの感度・描画の速さは違います。
- **フレーム時間は目安です。** 2コアのマシンで2つのページを同時に動かしており、他の作業も同じマシンで動いていました。
- 刷ったときの持ち越し時間は、毎回上限の6秒が付いています（直前の紙を自動で速く刷ったため）。後半の紙のめろめろの締め切りは持ち越しの影響を受けませんが、序盤（n=0・n=3）の締め切りは制限時間の20%なので、持ち越しの分（6秒×20%=1.2秒）長くなっています。持ち越しなしなら n=0 は 8.0秒、n=3 は 8.5秒です。

## 枚数の数え方

- **n** = それまでに刷った枚数（コードの `prints`、`setPrints(n)` で決める値、`cfg(n)` に入る値）。
- **何枚目** = いま挑戦している紙 = n+1 枚目。表では「n=44（45枚目）」のように両方書きます。
- 判定の締め切りを広げるのは n=7（8枚目）から（回転つまみが出る段階）。

### 操作の仕方（自動入力）

- つまみの値は互いに独立です（連動は版のずれにだけ効き、ほかのつまみの値は動かさない）。なので各つまみを「正解 − 今の値」だけ動かせば合います。左上から順に合わせました。
- **回す**: CDP の `Input.dispatchTouchEvent` で、つまみの円周（直径の36%の半径）に沿って指を動かす。16msごとに6度（予定は30度/80ms）。実際に出た速さは平均 0.30度/ms（最小0.22）、1目盛りおよそ0.1秒。回し終えたら100ms指を止めてから離す（弾いて回る動きを起こさない）。つまみとつまみの間は250ms。
- **タップ**: つまみの右側（＋）か左側（−）をタップ。1回で1目盛り、180ms間隔。つまみの間は250ms。
- 最後のつまみのあと250ms置いて「刷る」をタップ。
- 時間は「紙が出て操作できるようになった瞬間（`busy` が false になった最初のフレーム）」から「刷るを押した瞬間」まで。

### 連打の受け流し（0.4秒）の効き方

`__pz.tapGuard` は切らずに、別のページで確かめました（種1、390×844）。

- ゲーム画面に替わった直後のつまみタップ: 紙が出てから 24・129・226ms のタップは無視、329ms 以降は1回ずつ動いた（画面切り替えから0.4秒）。2枚目以降の紙では、つまみは受け流しの対象外。
- 紙が出た直後から、合わせた状態で「刷る」を約0.25秒ごとに押し続けると、**押している間はずっと受け付けない**（10回・2.4秒間すべて無視。0.5秒手を止めた次の1回で受け付けた）。早すぎる1回ごとに受け流しが0.4秒延びる作りのため。
- 1回早押ししてから0.5秒後に押すと受け付けた（56ms は無視、559ms は受け付け）。
- 実測の110枚では、紙が出てから「刷る」まで最短でも0.68秒（n=0 のタップ）かかっており、受け流しには一度も当たっていません。人の操作でも、紙の出た0.4秒以内につまみを合わせ終えることはまずないので、普通に遊んで当たるのは「前の紙の完成図を送るつもりで刷るを連打し続けた」場合だけです。その場合に合っていない紙を刷って肉球を失わないための仕組みなので、不具合ではなく意図どおりと判断しました（連打をやめない限り刷れない、という点だけ覚えておく価値があります）。

## (B) 式だけの照合（画面の操作とは別）

| 確かめたこと | 結果 |
|---|---|
| `best` = OP_LOOK + Σ(つまみの時間 + 目盛り×OP_STEP) + 連動×OP_LINK + OP_PRINT（ページの ax・sol・M から計算） | 110枚すべて一致 |
| `tMaxBase` = max(従来の制限時間, TIME_FIT(n)×best + 4) | 110枚すべて一致 |
| `tMax` = tMaxBase + 持ち越し | 110枚すべて一致（持ち越しは毎回6秒） |
| `dM`・`dU` の式（段階2以上は 1.3×best+0.5 / 2×best+1 と割合の大きい方） | 110枚すべて一致。段階2以上の88枚では、めろめろの締め切りはすべて 1.3×best+0.5 の側で決まっていた（20%の側ではない） |
| めろめろの締め切り ÷ best | 全体 1.33〜2.49。段階0・1（序盤22枚）は 1.42〜2.49（持ち越し込み） |

## わかったこと

1. **どの段階でも、自動の最速操作は best の 0.19〜0.49倍で終わった。** 後半（n=25〜60、26〜61枚目）は平均 0.23〜0.28倍（1枚ごとでは 0.19〜0.31倍）。best は「見て把握する」「合ったか確かめる」時間を含む見積もりなので、自動入力より長くて当然です。ここから言えるのは「画面や入力の仕組みの側には、best を超えるような隠れた待ちはない」ということまでです。人が best どおりに動けるかは、この計測ではわかりません。
2. **めろめろの締め切りに届かない紙は、自動入力では1枚もなかった。** 110枚すべてめろめろ。締め切りまでの余裕は最小でも6.8秒（n=3、4枚目）。後半ほど余裕が大きい（n=44〜60 で約19〜20秒）。
3. **後半の操作量は、指の動きだけなら5秒前後。** 6つのつまみ・目盛り計17〜24で、回しても、タップでも4〜6秒。後半の best（18〜19秒）との差の約13〜14秒は、式の上では OP_KNOB（つまみ1つ0.9〜1.5秒）と OP_LINK（連動1つ1.5秒）が占めています。つまり後半の締め切りが妥当かどうかは、指の速さではなく「見て判断する時間」の見積もりで決まります。ここは人の試遊でしか確かめられません。
4. **タップ1回180msは、OP_STEP（1目盛り0.15秒）より遅い。** 自動で180ms間隔のタップでも余裕で届いたので問題にはなっていませんが、タップだけで合わせる人にとっては、目盛りの多い紙ほど見積もりより時間がかかる方向にずれます。回す操作は1目盛り約0.1秒で、見積もりより速い。
5. **刷ってから次の紙まで、完成図を最後まで見ると2.64秒、送れば1.05秒。** どちらも紙の制限時間には含まれません（`busy` の間は時計が止まる）。
6. **不具合は見つかりませんでした。** 入力の取りこぼし、判定の食い違い、式とのずれ、画面外のつまみ、ページのエラーはいずれも0件。「刷る」の連打で受け付けが延び続ける動きは確認しましたが、上に書いたとおり意図どおりと判断しています。

## これは何を示さないか（もう一度）

- 人が遊んだときの時間・判定の取りやすさ（見て考える時間を含まない）。
- iPhone や GRAVITY のアプリ内での動き・描画の速さ・タッチの反応。
- 持ち越しのない紙（毎回6秒の持ち越しが付いていた）での序盤の締め切り。
- おたすけ、ラストチャンス、★特色（ローラーが1.7倍遅い）の紙。
- 弾いて回す操作（離す前に100ms止めて、弾きを起こさないようにした）。
